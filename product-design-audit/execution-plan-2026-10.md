## 1 目标与范围

将现有记账工具重构为由智能管家主导的个人账务管理 skill。用户提供数据、表达目标和补充无法判断的事实；管家负责整理入账、对账、维护数据质量、跟踪预算、分析变化和汇报结果。

本次重构包含以下已经确定的方向：

- 一个主 skill 和一个面向用户的总管家，按需加载记账、导入对账、预算、分析、报告、账务检查等专业职责。
- 所有角色、CLI、页面和报告共享统一账务内核与计算口径。
- 用户习惯保存在独立文档中，每次记账、导入或分析加载；通用 skill 不携带某个人的默认账户、消费习惯或沟通偏好。
- 数据结构可以演进，通过版本、结构说明、能力清单和迁移机制让所有角色使用一致规则。
- 允许按实际任务生成或修改扩展脚本，与系统脚本分开，经过验证、登记和启用后复用。
- 展示方式只服务于用户理解数据，不预设三个 HTML 模板或固定页面。对话为默认入口，按实际任务选择明细、图表、可下载报告或交互视图；可以暂不提供 HTML，确有复用需求时再提炼模板。
- 保留本地 JSON 和现有 CLI 入口作为首轮实现基础，渐进替换内部实现。
- 创建账本时询问是否启用 Git 历史及远程备份同步，保存用户选择；支持查看历史、恢复记录与跨设备同步，账本仓库与 skill 源码仓库分离。

本计划不安排立即修改正式账本，不默认启用定时任务、外部通知或新服务。真正的并行子 agent 是可选执行方式；普通记账无需启动多个 agent。

## 2 实施约定

1. **先明确账务语义，再拆模块。** 不能为了兼容旧实现而固化已确认的错误口径。
2. **兼容入口，显式迁移语义。** 保留常用账务命令和现有数据的读取能力；需要改变历史结果时生成差异说明，不静默改账。旧 HTML 专用入口可按展示方案停用或转向其他输出，明确说明替代使用方式，不为兼容入口强制保留旧模板。
3. **统一写入。** 角色和扩展提交提案，正式账本由核心服务在锁和版本校验下写入。
4. **按需加载。** 入口只保留共同流程与约束，专业流程、扩展说明按任务加载。
5. **配置优先。** 分类、提醒阈值、默认账户等用画像或配置表达；确有新的处理逻辑才生成脚本。
6. **事实与推断分开。** 保留原始证据，明确字段来源；不能把推测的账户、金额或因果关系写成确定事实。
7. **保留可回退状态。** 每次正式迁移保存数据、规则和扩展版本之间的对应关系，恢复时作为一致集合处理。
8. **用行为验收。** 不以拆了多少文件、增加多少角色作为完成标准。

已有设计文档作为背景资料。本计划统一后续范围；遇到旧文档与本计划冲突时，在对应实施阶段同步整理说明，避免维护两套互相矛盾的规则。

## 3 目标结构与责任边界

### 3.1 Skill 与角色

- **总管家**：加载上下文、理解目标、选择流程、汇总提案、组织写入、统一回复、维护跨轮次待办。
- **记账管家**：处理自然语言与单张凭证，生成交易和纠错提案。
- **导入对账管家**：识别账单格式、提取原始行、验证来源总额、识别重复和关联。
- **预算管家**：维护用户确认的预算，计算进度和预测，提出有依据的调整建议。
- **分析管家**：解释收支变化、异常和数据覆盖限制，提供可追溯指标。
- **报告管家**：基于统一报告数据包生成对话简报和周期报告，按任务与宿主能力选择合适的展示方式，HTML 仅是可选产物。
- **账务检查管家**：检查结构、口径和证据一致性，验证修改结果，管理复核事项。

用户画像和能力维护先作为共享流程，不增加常驻角色。需要并行时，专业 agent 接收同一版本的上下文，只返回候选数据、修改提案或分析结果。总管家负责合并与检查冲突。

### 3.2 代码分层

目标目录可在实施中按实际规模调整，依赖方向保持一致：

- `scripts/ledger`：兼容的命令入口。
- `scripts/ledger_tool.py`：逐步缩减为兼容适配与命令分发。
- `scripts/ledger_core/domain/`：金额、账户、经济事件、结算关系、预算、指标口径。
- `scripts/ledger_core/storage/`：JSON 读写、锁、版本检查、备份、变更记录。
- `scripts/ledger_core/services/`：入账、纠错、导入、画像、复核、报告等业务服务。
- `scripts/ledger_core/adapters/`：CLI、HTTP、文件来源和 OCR 适配。
- `scripts/ledger_core/extensions/`：扩展发现、兼容性检查、受限执行接口与迁移协调。
- Git 历史与同步服务：管理一致快照、远程状态、恢复提案及同步冲突，调用核心校验和提交服务，不绕过账务规则。
- `references/`：共同数据约定及各专业角色的流程；沿用现有文件或按需重组，不预建空目录。
- `assets/`：真正需要随包分发的资源；只有出现稳定复用需求时才纳入展示模板。

领域层不依赖 CLI、页面和存储；存储层不反向导入命令模块；接口层不自行计算财务口径。

### 3.3 每个账本的运行数据

兼容现有账本路径解析，按账本身份隔离以下内容：

- `ledger.json`：正式账务数据、预算、复核状态、账本修订号及必要变更记录。
- `user-profile.md`：用户明确规则、目标、沟通偏好和授权范围的权威文档。
- `observations.json`：从历史记录推导、可重新计算的模式，不自动等同于用户规则。
- `runtime.json`：当前有效结构、启用扩展、可用展示能力及兼容版本的能力清单；仅在存在模板时登记其版本。
- `schemas/`：核心结构引用和已登记扩展的结构定义。
- `extensions/<extension-id>/<version>/`：经过验证的用户或账本扩展、说明及测试样例。
- `templates/`：可选目录，仅在用户实际复用自定义展示模板时创建；不预建固定数量的模板。
- `work/`：一次性解析或转换脚本及中间产物，默认不注册为长期能力。
- `sources/`、`reports/`、`backups/`：来源证据、报告版本和恢复资料。

以上是目标职责划分，不要求一次性创建全部目录。原有自定义账本文件名和环境变量继续有效；多个账本共享目录时使用独立子目录或稳定账本 ID，不能仅凭固定文件名定位画像。

### 3.4 Git 历史与远程同步

创建账本时用一个简短问题让用户选择：不启用 Git、仅保留本地 Git 历史、启用本地历史并备份同步到远程。明确本地提交不等于上传，远程同步需要用户选择或确认目标仓库。用户已有明确选择时直接采用，不重复询问；尚未选择时可先创建本地账本，但不初始化 Git 或上传，后续可随时启用。

启用远程时说明目标、可见性、上传内容及同步时机。新建远程仓库建议使用私有仓库；复用已有仓库时检查实际可见性和内容，不能假定私有或覆盖已有内容。用户对自动同步的选择持续有效，在约定范围内不逐次确认；更换目标、扩展上传范围或改变可见性应重新取得相应授权。

- **仓库隔离**：默认每账本一个独立数据仓库，位于运行数据目录。不能因为账本位于源码目录下，就将数据提交或推送到上级 skill 仓库；不接管无关的现有仓库。
- **版本范围**：使用明确文件清单，保存账务数据、画像、结构定义、可移植能力信息及恢复所需的已验证扩展和自定义模板。来源附件、归档报告是否上传单独选择；未上传的附件不能宣称已远程备份。
- **排除内容**：不提交凭据、带令牌的远程地址、机器路径、锁文件、缓存、临时脚本、未完成事务和重复备份。账本仓库有自己的忽略规则，不混用 skill 分发规则；暂存文件时使用白名单。
- **本机设置**：远程连接、当前设备授权、同步状态和本机路径单独保存并排除出版本管理。可同步的画像表达偏好，但拉取或恢复的文档不能自动扩大当前设备的执行或上传权限。
- **一致快照**：每次成功的业务操作生成一个可识别的本地版本，批量导入作为一组记录；数据、画像、结构和扩展版本来自同一个已验证状态。提交摘要说明操作类型和数量，避免复制交易原文。
- **后台行为**：仅在宿主有运行能力时按用户选定时机自动同步；否则在当前调用中尝试或下次调用重试。分别显示“账本已保存”“历史已记录”“远程已同步”，断网或认证失败不撤销已成功的记账，也不重复记账。
- **跨设备同步**：先获取远程状态，在隔离副本中按共同祖先、稳定记录 ID 和变更记录合并，再通过核心校验后应用。不同记录的独立变更可自动合并；同一记录或规则的矛盾修改、删除与修改冲突需要保留双方并提出解决方案，不按最后写入时间覆盖。
- **历史恢复**：用户可以查看版本差异、撤销某次操作或恢复指定时点。先生成恢复提案并保留当前状态，校验账务、结构和扩展兼容性后形成新的恢复提交；常规恢复不重写共享历史、不自动强制推送。恢复整本账本时明确此后记录的处理方式，单笔撤销不丢弃无关的新记录。

Git 历史是可选的版本管理与同步能力，不替代业务变更记录、幂等控制和本地恢复备份。删除当前文件不等于删除 Git 历史中的内容；若用户要求清除历史数据，应作为单独操作处理，而非普通回滚。

## 5 最低行为验收集

以下场景贯穿各阶段，相关实现完成后必须验证实际结果：

1. **清晰记账**：输入“午饭 28”可以直接完成；画像没有默认账户时不冒充已知账户。
2. **固定金额**：用户明确设置固定金额时在范围内使用；仅有两次重复历史金额不能自动获得补金额权限。
3. **单次纠错**：修改一笔分类不形成长期规则；明确“以后都这样记”才写入画像。
4. **账户事实**：账户余额不足不导致擅自改到另一个账户；期初未知时不把计算余额当成已核实余额。
5. **垫付结算**：垫付 100、收回 60 后应收为 40，全部收回不增加个人收入或消费；工资与垫付同金额不误核销。
6. **坏账确认**：放弃追回有明确日期和金额，不能通过修改旧记录状态让历史期间无说明地变化。
7. **退款与转账**：保留原消费和退款；自身账户转账与信用卡还款不重复计入收入或支出。
8. **跨来源导入**：相同来源重复导入无新增，跨来源同一消费可关联，真实同金额消费不被合并。
9. **不完整数据**：缺账户、缺期初或缺日期覆盖时保留明确状态；报告不能把未记录说成没有发生。
10. **画像隔离**：两个用户或账本的默认规则互不污染，学习结果不会覆盖明确规则。
11. **结构演进**：新增项目字段后角色和实际使用的展示方式能发现相关能力；未知金额语义扩展不能被静默忽略。
12. **并发变更**：旧版本提案提交时发现账本或规则已变化，重新校验且不覆盖新数据。
13. **扩展脚本**：候选代码不自动执行，修改后验证失效，失败时正式账本不受影响，停用后不再被选择。
14. **提醒状态**：忽略或暂缓的相同事项不重复出现，新证据可以重新触发相关检查。
15. **报告一致性**：相同版本下对话、CLI、分析、月报及实际提供的图表或视图一致，多币种不直接混加，没有固定模板的报告也可追溯。
16. **迁移恢复**：迁移中断可恢复到一致状态，失败重试幂等，恢复旧版本不丢失迁移后新产生的记录。
17. **安装与按需展示**：分发包在独立目录可运行，无 HTML 模板或 Web 服务时基本流程完整；旧展示入口已妥善停用或调整，无失效引用；可选视图失败时可回退到可读的结论与明细。
18. **建账选择**：创建时明确询问或沿用已知 Git 偏好；未选择不上传，选择仅本地不访问远程，之后可以启用或停用。
19. **范围与仓库隔离**：账本数据不会进入 skill 源码仓库；只上传约定文件，凭据、本机路径、临时脚本和未选附件均不在提交中。
20. **离线与失败恢复**：断网、认证失败或本地 Git 提交失败不丢账；恢复后重试不重记，分别准确报告本地保存和远程同步状态。
21. **跨设备冲突**：独立变更经过校验可合并，相同来源不重记；同一交易矛盾修改或删除冲突保留双方，不自动强制推送。
22. **历史恢复与新设备**：回滚产生新的可追溯提交；整本恢复明确后续记录处理方式；新设备不自动执行同步来的扩展代码，也不继承旧设备的上传授权。

## 6 里程碑与实施顺序

- **M1 账务基础可信**：P0、P1、P2 完成。现有入口可用，共享口径成立。
- **M2 个性化与扩展受控**：P3、P4、P4A 完成。画像独立，结构和脚本的变化可被发现与验证，可选 Git 历史、恢复和同步可用。
- **M3 管家流程完整**：P5、P6 完成。导入、预算、分析、报告和复核形成可持续流程。
- **M4 展示与发布可用**：P7、P8 完成。按需展示和无 HTML 的基本流程通过验收，迁移与安装验证完成；不以独立页面或固定模板交付为前提。

默认依赖顺序为 P0 → P1 → P2 → P3 → P4 → P4A → P5 → P6 → P7 → P8。P5 不以启用 Git 为前提；展示数据约定可在 P1 确定，P6 的单笔记账与复核流程可在 P3、P4 后先接入。P7 的基本展示和旧依赖整理需要完成，独立页面及模板按实际需求后续增加，不阻塞 P8；这些机会不自动启动并行 agent。

每阶段以小范围、可检查的变更交付，并附相关验证结果。出现新需求时先判断属于画像配置、扩展能力还是核心语义变化，再调整计划，避免把个别用户习惯重新写回系统核心。
