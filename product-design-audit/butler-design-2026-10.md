# 财务小管家 —— 功能设计

> 2026-10 重构设计（v2，含产品决策）
> 决策：管家**在对话内主动开口**、**支持定时汇报**、**给温和的消费建议**。

---

## 一、产品定义

### 一句话

> 一个替你看账、替你判断、主动告诉你的财务小管家。你只负责提供数据。

### 角色边界

| | 管家做 | 用户做 |
|---|---|---|
| 记账 | 理解一句话/一张截图，判断事件类型、分类、账户、关联关系 | 说一句话，或发一张图 |
| 归账 | 决定计入支出/收入/转账/垫付，自动关联退款与报销 | —— |
| 发现问题 | 主动扫描重复、异常、未收回、遗漏、矛盾 | —— |
| 汇报 | 主动说结论、依据、建议 | 听，或追问 |
| 决策 | 给出建议和选项，说明后果 | 最终拍板（大额、删除、改性质） |

**核心原则**：判断成本从人转移到系统。用户不需要懂账、懂字段、懂命令。

### 语气与人设

管家说话像一位**可靠、简短、有分寸的熟人**，不是报表系统。

- **先说结论，再说依据**。「这个月花得比上月多三成，主要是外卖」，不是「支出 ¥4,200，环比 +30%」
- **给数字，但数字服务于结论**。不输出没有观点的表格
- **有分寸**：小事一句话，大事才展开。没话说就不说话
- **不评判消费**，但会关心。说「外卖这个月 14 次了，要不要设个上限」，不说「你太浪费了」
- **诚实**：不确定就说「这笔我不确定」，不假装确定

### 反例（不要这样做）

```
❌ 支出 ¥8,399.00 · 收入 ¥15,088.00 · 净额 ¥6,689.00（一张表，没有观点）
❌ 「检测到 outlier: transaction_id=tx_xxx, ratio=205」（机器语言）
❌ 「根据您的消费数据，建议您减少非必要支出」（空话）
✅ 「这个月基本就是那台电脑，去掉它日常只花了 399。」
```

## 二、管家管什么：六个职责

设计以**职责**为单位，而不是以命令为单位。命令只是实现职责的工具。

### 职责 1：记账（Record）

**目标**：用户说一句话，账就记对了，不需要用户知道字段名。

| 用户输入 | 管家动作 |
|---|---|
| 「星巴克 38」 | 记支出 38，咖啡茶饮，微信零钱，立刻回一句「记好了，本月咖啡 ¥154」 |
| 「昨天打车 26，公司报销」 | 判断为**垫付**（应收），不记支出，记 `advance: open` |
| 「公司把 1200 打过来了」 | 判断为**偿还**，自动找到那笔垫付并核销，支出净额不变 |
| 「微信提现 500」 | 判断为**转账**，不计入收支 |
| 「这个不是我花的，帮同事付的」 | 记 `not_mine`，不计入收支 |
| 一张支付宝账单截图 | 识别多笔 → 展示确认表 → 导入 → 报告结果和发现 |

**关键设计**：记账不是「写入一条记录」，而是**一次完整的判断 + 汇报**。同一个入口，输出包含：

1. 记成了什么（事件类型、分类、金额、账户）
2. 为什么（依据）
3. 让本月变成了什么样
4. 有没有因此暴露新问题

### 职责 2：归账（Classify）

**目标**：判断「这笔钱在财务上到底是什么」，而不是「这笔钱叫什么」。

核心是**两条正交的轴**：

**轴 A：经济性质** —— 这笔钱是什么

```
spending    普通支出，计入支出
earning     真实收入，计入收入
transfer    自有账户间移动，不计收支
not_mine    不是我的钱，不计收支
advance     垫付/借出（应收），不计支出
```

**轴 B：结算进度** —— 结清了没

```
none        一次了结
pending     应收/应付中
settled     已收回
written_off 放弃（此时转为真实损失，计入支出）
```

**为什么这样分**：现状把这两个轴混在 `type`/`advance`/`excluded_from_totals`/`relation`/`tags` 五个字段里，导致同一个问题要在五处判断。分开之后，"这笔算不算支出"变成一次查表。

**实现策略（不破坏现有数据）**：
- 继续写现有的 `type`/`advance`/`excluded_from_totals`/`relation` 字段（兼容旧账本和 Web UI）
- 新增纯函数投影 `nature(tx)` 和 `settlement(tx)`，在**读时计算**
- 所有汇总、查询、汇报都走投影
- 旧账本无需迁移

### 职责 3：发现问题（Detect）

**目标**：账本自己会说话。管家定期扫描，主动发现人不会注意但会在意的事。

已实现 6 类检测，继续扩展：

| 类型 | 检测什么 | 例 |
|---|---|---|
| `negative_balance` | 账户余额为负（数据缺失） | 微信零钱算出来 -38 |
| `stale_advance` | 垫付长期未收回 | 45 天了还没收回 |
| `category_surge` | 某类支出突增 | 外卖从 6 笔涨到 14 笔 |
| `outlier` | 单笔远超平常 | 8000 是平时的 205 倍 |
| `habit_merchant` | 某商户高频 | 这个月星巴克 9 次 |
| `unspecified_spending` | 多笔无商户无分类 | 5 笔共 ¥320 归到「其他」 |

**待补充的检测**（设计上重要、当前缺失）：

| 类型 | 为什么要 |
|---|---|
| `duplicate_suspected` | 同一笔账导入了两次，会让支出虚高。**最高优先级** |
| `missing_recurring` | 每月固定支出（房租、会员）这月没记 |
| `budget_pace` | 按当前速度会超预算 |
| `income_missing` | 有支出但没有收入记录（可能漏记工资） |
| `category_drift` | 同一商户在不同月份被分到不同类别（归账不一致） |
| `account_stale` | 某账户很久没有余额变动（可能已废弃或漏记） |

### 职责 4：主动汇报（Report）

**三个层次的主动**：

**层次 1：每次对话开头** —— 极简问候（如果有事就说，没事不说）
```
早上好。有 2 件事想跟你说：
· 差旅垫付 1200 已经 45 天没收回
· 微信零钱余额算出来是负的，缺期初余额
```

**层次 2：每次记账之后** —— 汇报影响
```
记好了：星巴克 ¥38 · 咖啡茶饮 · 微信零钱
本月咖啡已经 ¥154 了，比上月整月还多。
```

**层次 3：定时汇报**（用户已选）—— 按周期主动生成
```
【本周】花了 ¥1,240，比上周少 18%。
外卖 6 次 ¥342，是本周最大一项。周六那天花了 ¥520，是一笔聚餐。
有 1 笔退款没对上，等我确认。
```

**定时机制的形态**：
- 不内置守护进程（违背「本地、简单、无服务」的设计）
- 提供 `ledger digest --since last-week` 之类的命令，输出**现成的汇报文本**
- 由外部调度触发（用户自己用 cron、或对话中的定时任务）
- 关键：**汇报文本由 CLI 生成**，保证准确、可复现，AI 只负责转述和追问

### 职责 5：建议（Advise）

用户选择了「给温和的消费建议」。设计原则：

**建议必须基于事实，不能是模板空话。**

```
❌ 「建议您合理规划消费」
✅ 「这个月外卖 14 次 ¥588，占了餐饮的 63%。如果设个月上限 500，超了我会提醒你。」
```

**建议的分级**：

| 级别 | 触发 | 语气 |
|---|---|---|
| 不说 | 数据太少、没有异常 | 沉默 |
| 陈述 | 有事实但无需行动 | 「这个月咖啡 9 次，¥342」 |
| 建议 | 有可改善的空间 | 「比上月多了 2 倍，要不要设个上限？」 |
| 提醒 | 已超或将超 | 「按这个速度月底要到 ¥6,200，超预算 ¥1,200」 |
| 干预 | 数据可能有错 | 「京东 ¥8,000 是平时的 205 倍，是不是记错了？或者和别的账重复了？」 |

**克制**：每次最多 3 条建议。宁可少说，不要唠叨。

### 职责 6：追问与确认（Ask）

**目标**：只在真正需要用户决定时开口，且问得聪明。

**判定规则**：

| 情况 | 动作 |
|---|---|
| 证据充分，含义唯一 | 直接记，事后说明 |
| 证据充分，但有两种合理解释且影响金额 | 问，给候选 + 推荐 |
| 证据不足 | 记下，标为待确认，追问时不打断 |
| 涉及删除/合并/改变收支性质 | 必问 |

**追问的质量**：

```
❌ 「这笔账的分类是什么？」（把判断推回给用户）
✅ 「『公司报销的车费 128』我记成了收入（公司把钱给你了）。
   如果你其实是先自己垫的、等着公司报，告我一声我改成垫付。」
```

**关键**：追问时**替用户想清楚选项**，而不是让他填空。

## 三、命令设计：入口收敛

命令是管家的工具，不该是用户的界面。目标：**用户和 AI 都只需要记住 4 个入口**。

### 主入口（4 个）

| 入口 | 干什么 | 覆盖的场景 |
|---|---|---|
| `ledger record "<一句话>"` | 记账，返回判断+汇报 | 记账、垫付、偿还、转账、退款 |
| `ledger brief` | 现状 + 待办 + 建议 | 「这个月怎么样」「我该做什么」 |
| `ledger digest --since <周期>` | 生成可直接发送的汇报文本 | 定时汇报、周报、月报 |
| `ledger ask "<问题>"` | 回答具体问题 | 「上月外卖花了多少」「谁还欠我钱」 |

### 底层命令（保留，供 AI 内部使用）

`add` / `parse` / `update` / `delete` / `show` / `summary` / `list` / `find` / `advance` / `review` / `budget` / `account` / `habit` / `prefer` / `insight` / `doctor` / `audit` / `import-tsv` / `export` / `backup` / `render` / `serve`

**关键变化**：
- 保留全部底层能力（不砍功能）
- 但**面向用户的文档只讲 4 个入口**，底层命令在 reference 里作为「管家的工具箱」
- `record` 是 `add` 的语义化包装：多了「返回判断依据 + 主动汇报」

### 为什么是 `record` 不是 `add`

`add` 是数据库语言（添加一条记录），`record` 是人的语言（记一笔账）。同理 `brief`（简报）、`digest`（汇报）、`ask`（问）。

## 四、数据模型：两条轴

### 现状（5 个字段混在一起）

```json
{
  "type": "expense",
  "advance": "open",
  "excluded_from_totals": false,
  "relation": null,
  "related_transaction_id": null,
  "tags": ["报销"]
}
```

要回答「这笔算不算本月支出」需要同时看 5 个字段。

### 目标（两条正交轴）

```json
{
  "type": "expense",           // 保留：现金方向
  "advance": "open",           // 保留：结算进度（兼容）
  "..."                        // 其他字段不变
}
```

读时投影出两个明确的值：

```python
nature(tx)      # spending | earning | transfer | not_mine | advance
settlement(tx)  # none | pending | settled | written_off
```

**汇总规则集中成一张表**：

| nature | settlement | 计入支出 | 计入收入 | 计入余额 |
|---|---|---|---|---|
| spending | none | ✅ | | ✅ |
| earning | none | | ✅ | ✅ |
| transfer | any | | | ✅ |
| not_mine | any | | | ✅ |
| advance | pending | | | ✅ |
| advance | settled | | | ✅ |
| advance | written_off | ✅ | | ✅ |

这张表是**唯一**的收支判定依据。`summarize()`、`budget_progress()`、`advance list`、`brief` 全部走它。

## 五、关键流程

### 流程 A：记一笔普通支出

```
用户：星巴克 38

管家内部：
1. 解析 → 支出 38，咖啡茶饮，微信零钱（置信度 1.0）
2. 检查是否重复 → 否
3. 写入
4. 汇总影响：本月咖啡 154，比上月多
5. 生成回复

管家回复：
记好了，星巴克 ¥38 · 咖啡茶饮。
本月咖啡已经 ¥154，上月整月 ¥98，注意到时可以说一声。
```

### 流程 B：垫付与偿还（最容易记反账的路径）

```
用户：昨天打车 26，公司报销

管家内部：
1. 识别「报销」+ 未来时态 → 不是收入，是**垫付**
2. 记 expense 26, advance=open, category=交通
3. 不计入本月支出
4. 生成回复

管家回复：
记成垫付了：打车 ¥26，等着公司报销，暂时不算你的支出。
收回来的时候告我一声，我自动核销。

--- 两周后 ---

用户：公司把 26 打过来了

管家内部：
1. 识别「打过来」→ 偿还事件
2. 找 open 垫付中金额匹配的 → 恰好 1 笔
3. 核销，写 relation=reimbursement
4. 生成回复

管家回复：
核销了：打车垫付 ¥26 已收回。
这笔从头到尾没有影响你的支出，账目是干净的。
```

**这个流程是产品的试金石**。用户说「报销」两个字，可能意思是完全相反的两件事（钱回来了 vs 等着报），当前实现已能区分，但需要继续加固。

### 流程 C：定时汇报

```
（每周一早上，由外部调度触发）

$ ledger digest --since last-week

【本周账单摘要】
花了 ¥1,240，比上周少 18%。

主要开销
· 外卖 6 次 ¥342（本周最大一项）
· 周六 ¥520，是一笔聚餐
· 交通 ¥86

需要你确认
· 有 1 笔退款 ¥89 没找到原始支出，是哪一笔？
· 外卖这个月已经 14 次了，要不要设个 ¥500 的月上限？

数据看起来没问题。
```

**设计要求**：这段文本由 CLI 直接生成，AI 可以直接转述，不需要二次加工。保证准确。

## 六、与现状的差距

| 职责 | 现状 | 差距 | 优先级 |
|---|---|---|---|
| 记账 | `add` 只写数据，不汇报 | 缺语义化入口 `record` + 汇报 | **P0** |
| 归账 | 5 字段散落，规则在 `summarize` 里 | 缺投影函数和规则表 | **P0** |
| 发现问题 | 6 类，缺重复检测 | 缺 6 类，尤其 `duplicate_suspected` | **P1** |
| 主动汇报 | 只有 `show` 被动输出 | 缺 `brief`（已实现雏形）、`digest` | **P0** |
| 建议 | 基本没有 | 缺建议分级和表述 | **P1** |
| 追问 | 规则写在 SKILL.md，三处重复 | 缺统一判定表 | **P2** |

## 七、实施顺序

按「用户可感知度 × 正确性风险」排序：

### 第 1 步：归账规则收敛（正确性基础）
- 实现 `nature()` / `settlement()` 投影
- 把 `summarize()` 里 5 处散落的判定收敛成规则表
- **不改变任何行为**，只是重构，用现有测试验证

### 第 2 步：`record` 入口（用户感受最直接）
- `add` 的语义化包装
- 返回：判断依据 + 影响 + 新发现
- 这是用户每次记账都会碰到的界面

### 第 3 步：`brief` 完善（已实现雏形）
- 建议分级
- 待办统一（已实现 `collect_open_items`）
- 数据不足时诚实说话

### 第 4 步：`digest`（定时汇报）
- 生成可直接发送的文本
- 支持 `--since last-week / last-month / since:<日期>`

### 第 5 步：补充检测（重复、缺失周期、类别漂移）

### 第 6 步：文档重构（SKILL.md 从命令手册改为行为准则）

## 八、明确不做

| 不做 | 理由 |
|---|---|
| 内置守护进程/常驻服务 | 违背「本地、简单、无服务」原则。定时由外部调度，CLI 只负责生成文本 |
| 接入 LLM 做判断 | 判断必须可复现、可测试。CLI 出证据和结构，AI 负责措辞 |
| 自动改账 | 管家可以建议，改账必须经用户确认或明确规则 |
| 砍掉底层命令 | 它们是管家的工具箱，只是不作为用户界面 |
| 引入数据库 | JSON + 文件锁在这个规模下是正确的，迁移成本远超收益 |
| 评判用户消费 | 给建议，不道德审判 |

## 九、验收标准

设计做对了的标志：

1. 用户说一句话就记完账，且知道「记成了什么、为什么、有什么影响」
2. 用户问「这个月怎么样」，得到的是一段有观点的话，不是一张表
3. 垫付 → 偿还的完整链路不出错，支出不虚增
4. 有任何该处理的事，管家主动说，不等用户问
5. 能定时输出一段可以直接发给用户看的汇报文本
6. AI 对每个判断都能说出依据，也能说出「为什么不是另一种」
7. 用户全程不需要知道「字段」「状态」「命令」这些概念
